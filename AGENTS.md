# AGENTS.md

Windows desktop GUI-automation agent ("ProLight"). Console-only, **non-admin**, asyncio. It perceives the desktop (window capture + DeepSeek vision) and acts on it (SendInput mouse/keyboard). No tests, lint, build, or CI.

## Run

- `python main.py` from the repo root (use `.venv`). Needs `.env` with `DEEPSEEK_API_KEY_MASTERMIND` and `DEEPSEEK_API_KEY_HELPER`.
- Interactive `ProLight> ` console: type a task; `/q` `/quit` `/exit` to stop, `/compress` to force context compression, `/learn [label]` / `/learn stop` to control a learning session deterministically (no LLM). `load_dotenv()` has no path, so `.env` is found only when CWD = repo root.
- Static check only: `python -m py_compile <files>`. There is no test/lint/typecheck command.
- First launch can look hung: cold imports are slow under endpoint protection (`import openai` ~77 s cold, ~5 s warm; `scipy` adds a few seconds). Start once and wait.

## LLM / vision

- One provider for everything: DeepSeek `deepseek-flash` (reasoning **and** multimodal), `base_url=https://api.deepseek.com` (`agent.py:20,83`, `lib/vision_client.py:22`).
- Key lookup is `DEEPSEEK_API_KEY_<AGENT_NAME>` → fallback `DEEPSEEK_API_KEY` (`agent.py:86`). Agents are `MASTERMIND` and `HELPER`, so the name is load-bearing.
- `deepseek-flash` is a reasoning model: give vision calls a generous `max_tokens` or `content` returns empty (reasoning eats the budget). `analyze_messages` falls back to `reasoning_content`.
- Images are downscaled to max side 1600 px and JPEG-compressed (q80) before sending (`vision_client.py`).

## Architecture

- `main.py` → `app.start_app()`: builds a global `agent`, a global `request_queue`, one sequential `worker()`, and the console loop.
- Request flow: console → `{"type":"user","prompt":...}` → `worker()` → `components/cmd_line.py` → `agent.run_with_crash_recovery()`. Only the `user` type is handled.
- Shutdown: `get_command()` reads stdin on a **daemon thread from a dup of fd 0** — not `sys.stdin`. `asyncio.to_thread(input)` hangs exit (asyncio.run joins the default executor and the thread never returns), while a daemon `input()` crashes finalization (`_enter_buffered_busy ... due to daemon threads`) by holding stdin's buffer lock. `start_app()` waits with `asyncio.wait(..., FIRST_COMPLETED)` and cancels the survivor, so `/q`, EOF, and Ctrl+C all exit cleanly (`main.py` catches `KeyboardInterrupt`).
- `lib/` = low-level layers: `winapi.py` (ctypes user32/gdi32/kernel32/dwmapi), `input_backend.py` (SendInput + WM_ fallback), `ui_tree.py` (pywinauto UIA control discovery), `image_ops.py` (crop/grab/pixel-diff), `overlay.py` (on-screen user feedback), `vision_client.py` (transport), `vision_agent.py` (vision sub-agent), `console.py`, `profiles.py`/`router.py`/`discovery.py` (deterministic profiles/states), `session_analysis.py` (learning-session synthesis), `workflow_runner.py` (deterministic workflow execution).
- `builtin_tools/` = the agent's tools; `system_prompts/` = the runtime prompt, split into `system_prompts/fragments/*.md` (one per tool group + `operating`). `lib/instruction_planner.py` deterministically selects fragments + tool groups per run (see Tools). `core.md`/`desktop.md`/`tools_guidelines.md`/`learning.md` remain as reference aggregates.
- `agent.py`, `context_manager.py`, `tool_registry.py` originated as verbatim copies of the sibling iNysha project; `context_manager.py` has since diverged (token-driven compression), and `tool_registry.py` hardcodes the `builtin_tools` package name — keep it.
- Memory/compression (`context_manager.py`): the trigger is **token-driven** — `get_assembled_tokens()` (base prompts + persistent + compressed + masked + sliding) vs `max_tokens` at `COMPRESS_TRIGGER_RATIO` (0.70), not message count. `agent.py` MUST set `messages.base_prompt_tokens` or the budget under-counts. Summaries are parsed from `## Heading` / `**Heading:**` sections (the `Narrative` is capped to ~1-2 sentences); `data/last_compression.txt` is seeded into `_compressed_dicts` on load instead of being injected as a base prompt (avoids duplication).
- Compression is **deferred**: automatic compression runs only when `run()` produces its final answer (background task, `_maybe_compress_after_run`) — never mid-loop, even if the budget is exceeded. `run()` first awaits any in-flight compression (`ContextPool.await_compression()`) so the next run appends to a stable context. `/compress` calls `compress(..., force=True)` (bypasses the ratio gate via the request queue). `DEFAULT_MAX_TOKENS` is 300K against the model's 1M hard limit, so a single over-budget run cannot hit the hard limit.

## Tools

- Tools MUST be `async def`; the registry awaits them.
- Each module defines a bottom-level `TOOL_DEFINITIONS = [(name, func, description, params_schema), ...]` plus `register_all(registry)` looping over it. Return a string (modules use a local `_dump()` = `json.dumps(..., ensure_ascii=False)`).
- Schema property keys must match the function's kwarg names exactly; params with defaults must NOT be in `required`.
- New module file → add it to BOTH the import list and the `register_all()` body in `builtin_tools/__init__.py`.
- `reload_tools` hot-reloads the submodules and the package `__init__.py`, so a new module added to that import list is picked up without a restart.
- Per-tool timeout defaults to 120 s but is configurable via `registry.set_timeout` (`ask_user` = 600 s); `agent.py:138` reads it per call. The agent loop caps at 50 iterations (`agent.py:356`).
- **Partial prompt/tool injection** (`lib/instruction_planner.py`): each run gets a deterministic `PromptPlan` (phase + fragment list + tool groups) from goal keywords and the foreground window's guide; `agent.set_instruction_plan` swaps `_base_prompts` and recomputes `messages.base_prompt_tokens`. `llm_request` passes only `registry.get_openai_tools(groups=self._active_groups)`. Every tool module tags its tools with a module-level `GROUP` (`perception`/`uia`/`vision`/`locate`/`probe`/`mouse`/`keybd`/`learning`/`workflow`/`overlay`/`fs`/`edit`/`apps`/`meta`); `meta`+`perception` are always on. The model can unlock more via `enable_tools(groups=[...])` → `agent.enable_tool_group`. The planner has a `workflow` phase (goal contains run/follow/execute/resume + "workflow") that pulls in `workflow`+`learning`+`uia`+`actuation`+`locate`+`vision`+`apps`+`overlay`.
- When you add a tool, set the module's `GROUP` and document it in the matching `system_prompts/fragments/<group>.md` (the planner injects fragments selectively).
- **Perception is snapshot/diff** (`builtin_tools/win_tools.py` + `lib/window_state.py`): `win_snapshot` returns identity, focus, menu, UIA controls and OCR text in ONE call, each with an id (`c7`/`t3`/`m2`); `win_changes` returns only the delta (UIA/OCR/pixel) and can `wait_for` an element. Ids are stable across snapshots (one-to-one identity matching). Act by id via `win_click_control(id=...)` / `win_set_control_text(id=...)` / `mouse_click(id=...)`. `win_changes(label=...)` accepts a custom label **or** the `snapshot_id` returned by `win_snapshot` (`window_state.get` resolves both). `lib/window_state.py` also does the Chromium a11y auto-enable (via `winapi.send_getobject`, `WM_GETOBJECT`/`UiaRootObjectId`). Chromium renderer content sits in a `Document` **7-8 levels deep** — beyond the snapshot's depth-3 walk — so a11y is detected with a depth-independent query (`ui_tree.count_documents`), and `accessibility_enabled` is `documents>0 or coverage=="good"` (the old `len(selected)>=5` test falsely reported "off").
- Text reading (`builtin_tools/win_tools.py` + `lib/ui_tree.get_text`): `win_read_text(hwnd)` dumps a window's accessible text (no OCR). For Chromium it targets the `Document` subtree (`descendants(control_type="Document")`, then its `Text`/`Hyperlink` descendants) — deep, depth-independent, and free of browser-chrome noise; `TextPattern.GetText` is unusable under comtypes (`AttributeError`), so names/values are the effective path. Native apps fall back to the bounded walk; one a11y-enable attempt then an OCR fallback. Bulk clipboard: `clipboard_get(max_chars/full)` + `clipboard_save(path)` (writes to `data/clipboard/`, read with `fs_read`).
- OCR (`lib/ocr.py`): Windows.Media.Ocr via modular PyWinRT (`winrt-*` packages in `requirements.txt`), run on a dedicated worker thread (own asyncio loop, like `ui_tree`). `recognize_auto` tries every installed language and keeps the richest (needed for Cyrillic). Windows OCR packs: `en-US`, `ru`.
- UI Automation actions (`builtin_tools/uia_tools.py`, backed by `lib/ui_tree.py`): `win_click_control`, `win_set_control_text`. Discovery moved into `win_snapshot` (the old `win_enum_controls`/`win_get_control_rects`/`win_find_controls`/`win_wait_for` tools were removed). UIA runs on one dedicated STA worker thread (`lib/ui_tree._run`); `sys.coinit_flags = 2` must be set before comtypes/pywinauto are imported.
- Deterministic locator (`builtin_tools/search_tools.py`, backed by `lib/image_ops.py` using numpy + scipy): `screen_find(kind="color"|"template"|"text")` — colour blobs (`scipy.ndimage.label`), FFT template match, and OCR text search. Replaces `screen_find_color`/`screen_find_template`. Returns screen coordinates. `image_ops.snap_box` refines a fraction/approximate box to exact pixels (used by `vision_locate`).
- Focus/input reliability: `win_focus` returns `keyboard_focus` (via `GetGUIThreadInfo`); `win_ensure_foreground(probe=true)` injects a benign key and returns `keyboard_delivery` (`winapi.verify_keyboard`), distinguishing `mouse_ok` from `keyboard_ok`. `keybd_*` accept an optional `hwnd`, re-attempt focus once, and refuse loudly if it still lacks keyboard focus (SendInput fails silently otherwise). `mouse_wheel(verify=true)` returns `screen_changed` (false = nothing scrolled). `win_get_foreground` was removed (the snapshot's `focus` covers it).
- Discovery probe (`builtin_tools/probe_tools.py`): `screen_probe(x, y, action="hover"|"click"|"scroll", ...)` — BEFORE/AFTER pixel diff; auto-focuses for click/scroll (a wheel needs the window focused), `undo_hotkey` for clicks, `undo` for scroll. Used by the learning discovery pass.
- **Workflow execution** (`lib/workflow_runner.py` + `builtin_tools/workflow_tools.py`, group `workflow`): a learned workflow has an executable sidecar program `workflows/<task>.workflow.json` (ordered steps `{id, app, state?, control?, action}` referencing apps/controls by name). `start_workflow(name)` loads/starts a run; `run_workflow_step()` executes the current step **deterministically** — it finds the app window (program hint → profile `trigger`), snapshots it, `router.route`s the guard `state` and `router.resolve_named`s the control, then acts by element id (else centre); `wait_state` polls until the expected state. A step that doesn't resolve returns `needs_llm: true` + the live state (`state_id`, available `controls`) and does **not** advance — the agent falls back to `win_snapshot`/`screen_find`/`vision`, acts, then calls `run_workflow_step` again to resume. Progress persists in `data/workflow_run.json`. `save_workflow_program`/`load_workflow_program`/`list_workflow_programs` manage programs; `workflow_status`/`workflow_reset` show/reset the run. `session_analysis.build_workflow_program` auto-drafts `workflows/_draft_<label>.workflow.json` (a `focus` step per app switch; a guard `state` = the app's *previous* state; a `wait_state` after an action that changes state; a `skip_if_state` toggle guard; `network_disruptive: true` for a VPN app). Drafts are written to `data/tmp/` (never `workflows/`) and `start_workflow` refuses them unless `allow_draft=true`. A `network_disruptive` program does **not** start until `start_workflow(..., confirm=true)` — the agent warns the user first; the run file persists through a dropped connection so `run_workflow_step` resumes, and `resumable: true` marks any non-advancing step. A step with no live window returns `needs_llm: true` + `needs_app`/`running`/`hint`. The runner captures with `max_text=160`/`max_controls=120` (per-step `step["ocr"]` overrides) and reports the scope in `result["snapshot"]`.
- **Discovery & smaller additions**: `list_tools(group=None)` (group `meta`) lists every registered tool (`name/group/purpose/params`) — the injected schema is group-scoped, but tools are callable regardless, so this is how the agent discovers capabilities (`enable_tools` names are generated from `instruction_planner.ALL_GROUPS`). `fs_json_query(path, expr)` queries JSON/JSONL with a dotted path + optional `| key=value` filter; `fs_grep` reports `engine=regex|literal` and `scanned_bytes`, and notes when a pattern's regex metacharacters were searched literally (`regex=false`). `win_snapshot` surfaces `window.chromium_a11y` (`enabled`/`disabled`/`unknown`) and a relaunch hint when renderer accessibility is off.

## Overlay (user-visible feedback)

- `lib/overlay.py` draws feedback the *human* sees but captures do not: a frame around every grab (from `image_ops.grab_screen`/`grab_window`), a persistent bottom-right status HUD, click rings and key/typing toasts (from `input_backend`), and deliberate `highlight` boxes. A dedicated daemon thread runs a real `GetMessage` pump; public calls are non-blocking (`_enqueue` + a wake message, ~0.2 ms round-trip).
- Overlays are **layered** windows (`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST`) rendered with `UpdateLayeredWindow`, so they are click-through and never steal focus. Layered windows **cannot** use `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` (it fails with err 8), so capture-invisibility is a **capture gate**: `overlay.begin_capture(rect)` / `end_capture()` hide only the overlays intersecting the grab for its duration; `image_ops` wraps every grab with it and shows the capture frame *after* the grab. Only large captures that include the HUD (bottom-right) cause a brief blink.
- Ambient feedback is gated by `PROLIGHT_OVERLAY` (default on; `0`/`false`/`no`/`off` disables). Deliberate `highlight` calls always draw, even when ambient is off.
- Tools (`builtin_tools/overlay_tools.py`): `highlight_area(regions, label, color, persist, duration)` and `highlight_clear(token)`; `ask_user(..., highlight=..., highlight_label=...)` outlines a region while asking (cleared on answer). `app.py` wraps `registry.call_tool` to drive the HUD; `components/cmd_line.py` sets thinking/done.
- Do NOT make overlay windows non-layered to try to use `WDA_EXCLUDEFROMCAPTURE`: a non-layered `HTTRANSPARENT` window does **not** pass clicks through cross-thread (verified — the click is swallowed), which would break the agent's own input.

## Vision sub-agent

- `lib/vision_agent.py` (`VisionAgent`, singleton via `get_vision_agent()`) is a **separate** assistant on the **HELPER** key (`DEEPSEEK_API_KEY_VISION` → `_HELPER` → `DEEPSEEK_API_KEY`). Calls are **one-shot** (system prompt + the current crop only) so screenshots never touch the main agent's context or prefix cache and a stale frame can never bias a fresh observation.
- It looks at small regions/controls, not whole windows: `look()` crops via `lib/image_ops.py` (mss screen grab, or PrintWindow when occluded), saves to `data/vision/`, and records labelled *watches*.
- `compare(label)` re-captures and sends BEFORE+AFTER images in one request; `changed(label)` is a pixel-diff with **no** LLM call — call it first (via `vision_compare(pixel_only=true)`) to avoid a needless vision request.
- `locate()` asks the model for element boxes as **fractions** of the crop (the model is reliable at fractions, not pixels), then converts to pixels and refines with `image_ops.snap_box`. Boxes are hints — exact geometry still comes from UIA/OCR/colour.
- Cross-request continuity is **structural**, not conversational: a labelled `watch` (region + last image) drives `compare`/`changed`; the main agent carries the text answers in its own context. There is no vision-side message history.
- Tools: `vision_look` (also handles an image `path`), `vision_compare` (with `pixel_only`), `vision_forget` (with `list_only`). `win_snapshot(vision_query=...)` routes through the same agent (so all live vision uses the HELPER key).
- Do NOT call `lib/vision_client.analyze_image`/its shared `_get_client()` directly: that default client uses the **MASTERMIND** key (`vision_client.py:32`) and is a dead path. `vision_agent` always passes its own HELPER client into `analyze_messages`.

## Windows / input gotchas (hard-won)

- `import lib.winapi` calls `ensure_dpi_awareness()` at import time → all coordinates are physical pixels. Do not rescale.
- Call `force_utf8_console()` (`lib.console`) before the first print/log; Cyrillic titles/answers otherwise crash or mojibake. `main.py`/`app.py` already do — do the same in any new entrypoint.
- SendInput only reaches the **foreground** window: `win_focus(hwnd)` and verify before mouse/keyboard input.
- **UIPI**: a non-admin process cannot send input to elevated (admin) windows — those targets are off-limits.
- UIA discovery is the reliable locator for native Win32 controls; browsers/Electron/1C/custom-drawn UIs often expose an empty/poor tree — `win_snapshot` reports `uia.coverage` and falls back to OCR text / `screen_find`.
- `win_send_message` (PostMessage WM_*) is a fallback for standard Win32 controls only; browsers/Electron/1C/custom UIs ignore it.
- Menu bars are NON-client area, so `GetClientRect` excludes them — `win_snapshot` includes menu items (id `m*`) with screen rects; click those, not client-relative offsets.
- `winapi.capture_window` returns `None` if both PrintWindow flags fail (never an uninitialized bitmap).

## Learning DB

- `interaction_guides/<key>.md` and `workflows/<task>.md` are the agent's learned-fact databases, managed by `lib/learning_db.py` + `builtin_tools/learning_tools.py` (see `system_prompts/learning.md`). Guide key resolution: explicit name → window-title tail → title head → **tab host** (`web.max.ru`→`max`, from `WindowState.active_url()`) → process name (`guide_candidates(url=...)`). Neither dir is gitignored; `workflows/` is created on demand.
- **Structured profiles + deterministic router** (`lib/profiles.py`, `lib/router.py`, `builtin_tools/profile_tools.py`): `interaction_guides/<key>.profile.json` is a machine-readable companion to the `.md` guide — `trigger` (process/title/url), `states[]` (each with `detect` rules over a `WindowState`, an injected `text`, and named `controls`), and `footprints`. `Element.stable_key()` (`lib/window_state.py`) is the cross-run element identity (`automation_id` else `type:name`); `WindowState.footprint(with_rects=True)` builds the per-state signature. After each tool batch, `agent._maybe_route()` calls `router.route(profile, window_state.get())` — with no LLM — and on a state match injects the result as `PromptPlan.volatile` (named controls already resolved to live ids) and widens tools to `uia`+`mouse`. Tools: `load_app_profile`, `save_app_profile` (full replace **or** typed deltas `add_state`/`patch_state`/`remove_state`/`patch_trigger`/`set_initial_text`, which auto-bump `version` and return a per-op diff — no whole-JSON rewrite), `route_app_state`, `resolve_app_control`, `discover_app`, `execute_app_control`. `lib/discovery.py` builds a profile deterministically from a live `WindowState` (regions, named controls, detect rules, footprint) — no LLM; `execute_app_control` acts on a named control (click/hotkey/focus) without an LLM. Rules are scored **most-specific-first** (`_spec_specificity`: a longer matching Pane name outranks a substring), and `route()` returns `also_matched` (runner-up state ids) plus `footprint_ok` that is **consistent** with `missing_keys` (any missing key ⇒ `false`) and `footprint_ratio`; `profiles.shadowed_rules` flags overlapping/substring rules in `validate`. `find_profile` is **URL-aware** (`WindowState.active_url()` reads the Chromium omnibox; a `url_contains` constraint is ignored when no URL is available, and `also_matches` aliases let one web-app profile claim its tab host). `min_controls` is skipped when the a11y tree is empty (Chromium), and `route()` includes `rejections` (`[{id, reason}]`) explaining why states failed. Coordinate controls accept `{"match": {"click": [x,y]}}` / `click` / `center` / `x`+`y` in both `resolve_named` and `resolve_controls`. State management tools: `rename_profile_state` (accepts a `{old:new}` map), `delete_profile_state`, `delete_profile_footprint`, `sync_profile_guide` (recompute the `guide_synced` hash + managed block).
- Learning mode records the user's real actions with `components/tracker.py` (pynput global hooks → `data/sessions/<label>_<ts>/`, kept last `MAX_SESSIONS`=10; `data/` is gitignored). Per click it saves a whole-window JPEG and the control under the cursor; **L1** also waits for the window to **settle** (pixel-stable, else accepted on timeout) and records a structured `WindowState` per action to `states.jsonl` (controls/menu/OCR/stable keys/footprint) plus an `app_timeline.json` of app switches (guide-key order). Capture is **two-phase**: fast UIA/menu only, adding OCR only when `uia_coverage` is poor/empty. The clicked control is recorded without a profile via its live `stable_key` (from the element identity) plus the runtime `id` matched by click point; a click is read at settle time and bound to the **next settled state of its own process** — a click in app A whose target is app B is **buffered**, never leaked into B, and claimed by B's later state. The footprint includes actionable-control **labels** in a `signature`, so a toggle (`Подключиться`→`Подключено`, same `automation_id`) is a **distinct state**; `session_analysis._sharpen_variants` then adds `uia_all` label rules (router supports `uia_all`) so the wrong variant can't match. The window where `/learn` was typed (`host_hwnd`) and shell/taskbar windows (`Shell_TrayWnd`/`NotifyIconOverflowWindow`/…) are skipped; keys come from process + a path-free title segment (`resolve_app_key`), so a shell path title can't become a key. `lib/session_analysis.py` (**L2**, no LLM) rebuilds those states, **injects each clicked control** into the state's `controls` (marked `verified`) so a workflow step always resolves, extends each `<key>.profile.json` **additively** (new states, refreshed footprints, merged named controls deduped by match spec; `merge_profile` matches by `router._state_score` **and** footprint similarity so a moved layout is a new state, reuses existing control aliases, and **seeds `<key>.md`** when missing) and writes a **cross-app workflow** draft (apps in order; steps reference `state` + named control) to `workflows/_draft_<label>.md` **plus an executable program** `workflows/_draft_<label>.workflow.json` (`build_workflow_program`). Tool: `summarize_learning_session`. The merge is **additive** (never removes states) and returns a per-app **diff** (`mode` create/merge, `before`/`after` states+bytes, `states_added`/`states_refreshed`/`states_removed`, `renames`, `guide` action); new states get a **semantic id** from their distinguishing control label (`_semantic_sid`, e.g. `подключено`), matched states reuse their existing id. An existing `.md` guide is never overwritten — only its managed `<!-- PROLIGHT:STATES -->` block is refreshed (`session_analysis.sync_guide_block`; `profiles.guide_stale` flags drift; `rename_profile_state` re-points an id with a `renames` map). `save=false` is a dry run (`dry_run:true`, drafts in `data/tmp/`). `learning_status` (tool) reports whether a recording is active, else the latest session on disk (`tracker.last_summary`); stopping twice returns `already_stopped:true`. `lib/router._verify_footprint` (**L3**) also compares `footprints[state].rel_rects` (tolerance `_MOVE_TOL`) → `moved_keys`/`layout_changed`, surfaced in `volatile_text`. Profile tools: `validate_profile`/`rename_profile`/`delete_profile`. Console: `/learn [label]` / `/learn stop` (deterministic, no LLM); while recording the overlay HUD shows `● learning: <label> — N step(s)` and a toast fires after each recorded step; `app._call_tool_with_overlay` preserves the learning HUD (via `tracker.overlay_status()`). The merge also dedupes by **detect-signature** (a byte-identical `detect` refreshes, never adds a twin) and drops the agent's **own console** from the recording (`session_meta.json` `host_process` + `agent_console`-tagged events; `dropped_console_records`/`dropped_console_events`). Drafts go to `data/tmp/` (never `workflows/`). More tools: `delete_profile_state`/`delete_profile_footprint`, `sync_profile_guide` (fix `guide_stale`), `rename_profile_state(renames={...})`, `learning_status`, `list_links` (dangling guide↔workflow references).
- `ask_user` (in `meta_tools.py`) is a **blocking** question: `app.ask_user_question` sets `_pending_question`, and the console loop routes the next line to it instead of enqueuing a request.
