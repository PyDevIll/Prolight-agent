Answers to your two inline questions
"Do all mouse tools use WM_ messages? Is that enough?" — No, and no. PostMessage(WM_LBUTTONDOWN/UP) works for standard Win32 controls and can target a background window without stealing focus, but browsers/Electron/1C/DirectX/UWP/custom-drawn apps ignore or mishandle synthetic WM_*. The reliable layer is SendInput (system input queue; requires the target to be foreground; visibly moves the cursor as you want). So: UIA for discovery/invocation → SendInput for mouse/keyboard → WM_ as a fallback for standard controls.

keybd_hold/keybd_release for Ctrl+S? — Prefer a single keybd_hotkey("ctrl+s"); it's atomic and less error-prone. Keep keybd_down/up only for genuine holds.

Key risks / constraints (non-admin)
UIPI: a non-admin process cannot send input to elevated (admin) windows. Any admin-elevated target app is off-limits. Must be documented.
DPI scaling: call SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2) at startup or GetWindowRect coords won't match SetCursorPos.
Image cost/latency: downscale + JPEG + crop-to-window; DeepSeek is a reasoning model, so give vision calls a generous max_tokens (reasoning eats the budget — I hit empty content at 50 tokens).
Cold imports: endpoint protection made import openai take 77s cold / 5s warm — same as iNysha.
